## 1. Goal

Arsenale already counts tokens per run from transcripts and can price them,
but only when the owner types prices in, only from a transcript, and only per
run. 1.3 makes cost a first-class, honest number:

1. Every run carries a **usage block with four meters** (input, output, cache
   read, cache write, the last split into 5-minute and 1-hour), its provider
   and model, from the transcript or from the tool's own report.
2. A **price file** the owner edits, with shipped list prices (source and date)
   that the owner can take with one command.
3. A **ledger**: cost per run, task, version and office, with "n/a" wherever a
   price is missing, never 0.
4. A **Savings page** and a weekly local report: measured spend first,
   suggestions second, every suggestion labelled "est." with its method. Tier
   suggestions are backed by the ATB-1 numbers; writing work is never routed to
   a cheaper model.
5. **Context packs**: a short brief per project (at most 1,500 tokens) that
   agents read first, through `arsenale context` and MCP `get_context`.
6. **Plan schema v1 task fields** on tasks (`type`, `size`, `tier`,
   `targetVersion`, `tokenEstimate`, `acceptance`), and a schema-v1 validator
   with a conformance fixture, so an outside planner's export (migration step
   M1) can be checked.

1.3 is the open-source release bar. Arsenale keeps watching only: nothing in
this spec starts, stops or steers an agent, and no change is applied by itself.

## 2. Scope

**IN**

- Four-meter usage block on `finish` (CLI and MCP), `provider`, `strategy`,
  `tier` kept on the finished record, `taskId` as an alias of the existing task
  link.
- Cost from a transcript (as today) or from four reported meters (new).
- Shipped price defaults, `arsenale prices`, a dashboard button to take them.
- `tools/ledger.cjs`, `arsenale ledger`, `GET /api/ledger`.
- Tier-suggestion rule v1, the Savings view, the weekly report, an
  owner-only "adopted" mark.
- Cache-read share per run and per week (transcripts expose it; see 3.1).
- Context packs: `arsenale context`, MCP `get_context`, `GET /api/context`.
- Task fields of schema v1 on create, update, list and get (CLI, MCP,
  dashboard task form).
- `tools/plan-schema.cjs`, `arsenale plan-check <file>`, the conformance
  fixture; the contract for the M1 export script.
- A public summary of the ATB-1 numbers that the suggestions cite.

**OUT** (later or never)

- `versions.json`, the Plan Dock, roadmap, "Plan into", `import-plan`,
  Today/Next, the work queue: 1.4.
- Share card export of the report; Pro history beyond 90 days: 1.4 at the
  earliest.
- Batch pricing, regional multipliers, fast mode: not priced in 1.3 (the
  ledger prices standard API rates only, and says so).
- Any automatic model change, any edit of an agent's `model:` line or of
  `tierModels` by Arsenale. Suggestions are text.
- Provider API keys, provider API calls, telemetry, any network call.
- Rule-compliance detection, compaction trend, memo/result reuse: 1.4 and 1.5.
- `fixRounds`, `gates` and `wallSeconds` as stored run fields (the schema's
  `run` shape lists them; 1.3 exports what exists and derives `wallSeconds`).

## 3. Data model

### 3.1 The run usage block

**What exists (1.2.2, verified in code).** `finishLocked` stores
`record.usage = {tokens, toolUses, durationMs, model}` and, only when the door
is not the CLI, `inputTokens`, `outputTokens`, `estimated`. The transcript
summary (`readTranscript`) already holds the five sums `input`, `output`,
`cacheRead`, `cacheWrite5m`, `cacheWrite1h`, per model in `models`, deduped by
message id; a transcript with only `cache_creation_input_tokens` counts it as
`cacheWrite5m`. `describe()` derives `tokTotal`, `tokSrc`, `costUsd`, `costWhy`
on read; cost comes only from a found transcript.

**New finish input (all optional, both doors).**

| Field (CLI JSON / MCP `usage`) | Meaning |
|---|---|
| `usage.inputTokens` / `input_tokens` | Uncached input tokens, summed over the run |
| `usage.outputTokens` / `output_tokens` | Output tokens |
| `usage.cacheReadTokens` / `cache_read_tokens` | Tokens read from the prompt cache |
| `usage.cacheWriteTokens` / `cache_write_tokens` | Cache writes when the tool does not split them; stored as given, priced as 5-minute writes |
| `usage.cacheWrite5mTokens` / `cache_write_5m_tokens` | 5-minute cache writes |
| `usage.cacheWrite1hTokens` / `cache_write_1h_tokens` | 1-hour cache writes |
| `usage.provider` / `provider`, or top-level `provider` | e.g. `anthropic`, `openai`, `google`; at most 40 characters of `[a-z0-9-]` |
| `usage.estimated` / `estimated` | `true` when the tool guessed; now kept from the CLI too |
| top-level `strategy` | free label such as `baseline` or `v1`, at most 40 characters |
| top-level `taskId` | alias of `issue` (see below) |

Rules:

- Each meter is a whole number `>= 0` (`Number.isSafeInteger`); anything else
  is dropped with a warning line, never stored as 0, and the run is still
  logged. A meter that was not given is absent, not 0.
- The CLI no longer drops the split meters (1.2 did). The reason for the drop,
  the Agent tool's last-context total, applies to `usage.tokens` only.
- `taskId` is stored in the existing field `issue` (`companyFields`), which
  1.2 already reads and links (`tasks.linkRun`). No second link field exists.
  When both are given and differ, `issue` wins and a warning is printed.
- `tier` (light, standard, heavy), today only on the active record, is copied
  to the finished record, as `officeId` and `kind` already are.
- Nothing is written to the active file beyond what `startRun` writes today,
  plus `tier` and `strategy` when given at start.

**Derived on read (never stored), added by `describe()`:**

| Field | Rule |
|---|---|
| `meters` | `{input, output, cacheRead, cacheWrite5m, cacheWrite1h}` from `transcript.tokens` when a transcript was found; else from the reported meters when **all four** of input, output, cache read and cache write (any of the three write fields) are present; else `null` |
| `meterSrc` | `'transcript'`, `'reported'`, `'estimated'` (reported with `estimated: true`) or `''` |
| `provider` | the given provider; else `anthropic` when `modelKey` is Opus, Sonnet, Haiku or Fable; else `''` (shown "unknown provider") |
| `cacheShare` | `cacheRead / (input + cacheRead + cacheWrite5m + cacheWrite1h)` from `meters`, or `null` |
| `costUsd`, `costWhy`, `costSrc` | see 3.3 |
| `wallSeconds` | `round(durMs / 1000)` |
| `turns` | `transcript.messages` when found, else `null` |

`tokTotal` and `tokSrc` keep their 1.2 rules, so budgets and existing pages
do not move.

### 3.2 The price file

Location and precedence are unchanged: `<home>/model-prices.json` (the owner's
copy) is read, else the template `tools/model-prices.json`. The template stays
empty, so a fresh install still shows "n/a" until the owner acts (and
`install.test.cjs` keeps passing).

New shipped file `tools/price-defaults.json`, read only by `arsenale prices
init` and the dashboard button "Use list prices":

```json
{
  "source": { "label": "Anthropic list prices, standard API", "url": "https://platform.claude.com/docs/en/about-claude/pricing", "fetched": "2026-11-18" },
  "models": {
    "Fable 5.2":  { "provider": "anthropic", "input": 8,   "output": 40,  "cacheRead": 0.20, "cacheWrite5m": 10,    "cacheWrite1h": 16 },
    "Opus 5.5":   { "provider": "anthropic", "input": 4,   "output": 20,  "cacheRead": 0.20, "cacheWrite5m": 5,     "cacheWrite1h": 8 },
    "Sonnet 5.5": { "provider": "anthropic", "input": 2,   "output": 10,  "cacheRead": 0.10, "cacheWrite5m": 2.50,  "cacheWrite1h": 4 },
    "Haiku 5.5":  { "provider": "anthropic", "input": 0.10,"output": 0.50,"cacheRead": 0.01, "cacheWrite5m": 0.125, "cacheWrite1h": 0.20,
                    "over100k": { "input": 0.50, "output": 2.50, "cacheRead": 0.05, "cacheWrite5m": 0.625, "cacheWrite1h": 1 } }
  }
}
```

USD per million tokens. Keys are `modelKey` names, which are the vendor's
display names (the pricing page lists no API id strings). Cache-write prices
match the page's multipliers (1.25x base for 5 minutes, 2x for 1 hour).

Owner file shape (additive to 1.2): top-level `source {label, url, fetched}`
and per model optional `provider` and `over100k`. A 1.2 reader ignores both
(it reads only the five price fields of `models[key]`).

Rules:

- `arsenale prices init` copies the defaults into the owner file when its
  `models` is empty; with entries present it refuses unless `--force`, and
  `--merge` adds only missing models. It writes atomically (`writeAtomic`) and
  prints the source and date. This is the only write; reading never writes.
- A price is used only when it is a finite number `>= 0`. A malformed entry
  reads as missing, so the run is "n/a" with `costWhy: 'prices'`.
- `over100k`: Haiku 5.5 is priced higher for prompts over 100,000 tokens. New
  transcript summaries add, per model, `long: {five sums}` for messages whose
  prompt (`input + cacheRead + cacheWrite`) exceeds 100,000 tokens; `long` is a
  subset of the model's sums, so a 1.2 reader prices it at base, as today.
  `costOf` prices `long` with `over100k` and the rest at base. A record
  without `long` (older ones, reported meters) is priced at base and gets
  `costNote: 'base rate; prompt size not recorded'`.
- `arsenale prices check` lists every `modelKey` seen in runs that has no
  price, and the file's `source.fetched` date; a date older than 90 days is
  printed as "check your prices".

### 3.3 Cost of one run

`costOf` (in `build-agent-dashboard.cjs`) becomes:

1. Meters from a found transcript: priced per model, as in 1.2, plus the
   `long` split. `costSrc: 'transcript'`.
2. Else, four reported meters and a model: priced with that model's price.
   `costSrc: 'reported'`, or `'estimated'` when `usage.estimated` is true.
3. Else `costUsd: null`, `costWhy: 'nodata'`. `usage.tokens` alone is never
   priced: it does not say what kind of token it counts.

Any missing price for a meter that has tokens makes the whole run `null` with
`costWhy: 'prices'`; there is no partial run cost. **Cost is never shown as 0
for an unpriced or unmeasured run.** A real zero (all meters 0, priced) is
`0` and shown as "$0.00".

When the company's `payModel` is `plan`, a priced cost is labelled
"API-equivalent", since the owner did not pay it per token.

### 3.4 Task fields (Plan schema v1)

Added to `company/issues/<KEY>-<n>.json`, all optional:

| Field | Values | Default when absent |
|---|---|---|
| `type` | `feature`, `bug`, `chore` | none (shown "—") |
| `size` | `S`, `M`, `L` (weights 1, 3, 8) | none; progress counts the task with weight 1 and says so |
| `tier` | `light`, `standard`, `heavy` | none |
| `targetVersion` | 1 to 20 characters of `[0-9A-Za-z.+-]`, e.g. `1.3.1` | none ("No version") |
| `tokenEstimate` | whole number `>= 0` | none |
| `acceptance` | text, at most 2,000 characters | none |

`type` is not `kind`: `kind` (kinds.cjs) is the kind of work that routes a
task to an office; `type` is the schema's bug/feature/chore. Both may be set.

Permissions (enforced in `tasks.cjs`, not in the UI):

- Board: all six fields on create and update.
- Supervisor: `type`, `size`, `tier`, `tokenEstimate`, `acceptance` on
  create only; never `targetVersion` (planning a task into a version stays
  the owner's, as in plan 3A).
- Agent: none (as today, comments only).

A bad value is refused with a form-ready sentence (`fail(400, ...)`), and
nothing is written. Each change goes to `history` like other fields.

### 3.5 Backward compatibility

- **1.2 opens 1.3 data unchanged.** Every new field is optional and additive.
  The company `schemaVersion` stays 1 (a bump would make 1.2 read-only).
  1.2's `updateTask` reads the whole task, changes its fields and writes the
  whole object back, so the six task fields survive a 1.2 edit. 1.2's
  `describe`/`costOf` ignore `meters`, `provider`, `strategy`, the new
  `usage.*Tokens` fields, `long` and the price file's `source`/`over100k`.
- **1.3 opens 1.2 data unchanged.** Missing fields read as absent. A 1.2 run
  with only `usage.tokens` keeps `costUsd: null` and shows "n/a"; a 1.2 run
  with a transcript prices exactly as before, plus the base-rate note for Haiku.
- **Reading never rewrites.** Ledger, savings, packs and the validator compute
  on read. The only writes are explicit: a finish, a task edit, `prices init`,
  `context --write`, the weekly report file and the adopted mark.
- Compatibility is proven by a test that runs the 1.2.2 code (read with `git
  show` at the 1.2.2 commit, as `offices-compat.test.cjs` does for 1.1) against
  a data folder 1.3 wrote, and skips with a reason when git or the commit is
  missing.

## 4. The ledger

`tools/ledger.cjs` exports `ledger(state, opts)`; `state` is `collect()`'s
output, so it reads nothing new.

- **Rows:** one per finished run (active runs are listed apart as "running",
  never summed into a closed period).
- **Joins:** task = `run.issue`; version = the task's `targetVersion`, else
  the version run's `version` (`run.versionRun` → `version-runs/<id>.json`),
  else "(no version)"; office = the stamped `officeId`, else the company
  resolver, as budgets do (`costEvents`).
- **Groups:** `by: run | task | version | office | model | week`, with
  `since`/`until` (ISO dates).
- **Each group** carries `runs`, `measured`, `unmeasured`, `tokens` (the
  `tokTotal` sum), the four meter sums (over runs with `meters`), `usd`,
  `usdRuns`, `usdMissing` and `usdStatus` with the meaning `spendOf` already
  gives it: `ok` (every measured run priced), `partial`, `na` (none priced),
  `none` (nothing measured).
- **Per task** also: `tokenEstimate` against measured `tokens`, the ratio, and
  `status`; **per version**: done weight over total weight (size weights,
  cancelled excluded), and cost per done weight-point when `usdStatus` is `ok`.
- **Display rule:** `ok` → "$X"; `partial` → "≥ $X" plus "N of M runs
  unpriced"; `na` → "n/a"; `none` → "not recorded". Never "$0.00" for these
  states.

## 5. Savings page and weekly report

### 5.1 What it shows (top to bottom)

1. **Measured this week**: spend (ledger `week`), runs, coverage (measured
   runs / all runs, priced runs / measured runs), cache-read share.
2. **Cost per done task and per done weight-point**, this week against the
   baseline. Baseline: the first 14 days with measured runs, or the date in
   `config.json "savingsBaseline"`. A change is shown only when both sides
   have at least 5 done tasks; otherwise "too few done tasks to compare".
3. **Suggestions** (top three by est. saving, then the rest folded), each with
   its rule, the runs it is based on, "est." on every number, and a "Why?"
   that shows the method and the ATB-1 rows behind it.
4. **Adopted**: suggestions the owner marked adopted, with the measured
   effect (cost per done weight-point of that kind of work before and after
   the date) once 5 runs follow; until then "measuring".

### 5.2 Tier-suggestion rule v1

Inputs per finished run: model family (via `modelKey`), the heavy list
(`config.json "heavyModels"`, default `["Opus"]`, plus `Fable`), `kind`, the
run's `tier` or its task's `tier`, and the task's `type` and `size`.

| Rule | Fires when | Suggests | Est. saving (ATB-1, one run per task per arm) |
|---|---|---|---|
| R1 light work on a heavy model | tier `light`, heavy model | the `tierModels.light` model | −95 % (T10 status scan, $0.26 → $0.01, 13/13 facts both) |
| R2 code on a heavy model | kind `build` or `verify`, heavy model, and not (`type: bug` and `size: S`) | the `tierModels.standard` model | −34 % median, range −24 % to −57 % (T2 −52 %, T5 −29 %, T6 −57 %, T7 −24 %, T8 −34 %; all hidden tests green) |
| R3 writing on a cheaper model | kind `docs`, `plan`, `research`, `content`, `legal` or `design`, model not heavy | keep or raise to heavy; no saving shown | none: a quality warning (T3 spec 12/20 with 3 factual errors; T9 research 17/20, below baseline) |

Never routed down, whatever the model: `docs`, `plan`, `research`,
`content`, `legal`, `design`, `security` and `review` (T4 review: −1 %,
no saving). R2 excludes tiny bug fixes because T1 cost 28 % more on the
standard tier (13 turns against 10). A run with neither a kind nor a tier gets
no suggestion.

Est. saving in USD = the run's measured cost × the rule's saving; when the run
is unpriced, the saving is "n/a" and the suggestion still shows. Suggestions
group by agent and rule ("builder: 6 runs, R2"). The "Why?" text states that
ATB-1 was a lite run (one repeat per task) and links to
`docs/benchmarks/atb-1.md`.

### 5.3 Weekly report

`arsenale savings [--week 2026-W47] [--json] [--write]` prints the page's
content as Markdown; `--write` saves it to `<home>/reports/savings-<week>.md`.
The running dashboard server writes last week's report once, on its first
state read in a new ISO week (local time), if the file is missing. No network,
no notification beyond the existing "waiting" channel (none is added). Costs
appear in the file; the share card with costs hidden is out of scope.

### 5.4 Adopted mark

`POST /api/savings-adopt {rule, agent, adopted: true|false}`, board only
(`requireBoard`), stored in `<home>/savings/adopted.json` with the date.
Marking a suggestion adopted changes nothing else; the owner edits the model
line or `tierModels` by hand.

## 6. Context packs

`tools/context-pack.cjs` exports `build(projectId)` → `{markdown, tokens,
projectId, signature}`. Tokens are estimated as `ceil(chars / 4)`; the limit is
**1,500**. Content, in order, each part shrunk step by step (clip lengths, then
counts) until the pack fits, and as a last resort cut with "…":

1. Project name, key, office, status.
2. Open tasks of the project, top 5 by priority then age: id, title, status,
   `type`, `size`, `tier`, `targetVersion`, acceptance (clipped).
3. Open decisions and open gates for the project (question, recommendation).
4. Last 3 finished runs: agent, model, `tokTotal`, cost or "n/a", summary.
5. House rules digest (the one `hello` returns), at most 6 lines.

It never includes a run's brief, file contents, transcript text, file paths
matching `SECRET_PATH`, or another project's tasks. `arsenale context
[--project <id>] [--write] [--json]` prints it; `--write` saves
`<home>/context/<projectId>.md`. `GET /api/context?project=<id>` and MCP
`get_context {project}` return it (read-only; any role). The pack regenerates
on read when its `signature` (mtimes of the project's task files, decisions
and gates) differs from the saved one. The MCP `INSTRUCTIONS` gain one line:
"Call get_context for the project before reading the repository."

## 7. M1: schema-v1 export from an outside planner

Migration step M1 needs a read-only export from the owner's planning hub
(HQ) that produces a schema-v1 file which passes Arsenale's fixture. Arsenale
ships the checker; the export script lives with HQ, because it reads HQ's own
database and HQ is a personal tool, not part of this repository.

**Arsenale side (`tools/plan-schema.cjs`, `arsenale plan-check <file>`):**

- Reads JSON (a JSON file is valid YAML, so HQ's `.hq/plan.yaml` reader still
  accepts it). No YAML parser is added; a non-JSON file is refused with
  "save the plan as JSON".
- Validates schema v1: `schema_version: 1`; ids
  `[A-Za-z0-9][A-Za-z0-9_.:-]{0,59}`, unique per list; phase status
  `todo|doing|done`; task status `todo|doing|review|blocked|done`; `type`,
  `size`, `tier`, `owner` enums; a task's `phase` must exist; decision status
  `open|decided`. 1.3 additions, optional: task `token_estimate` (whole number)
  and a `runs` list in the migration plan's `run` shape:
  `{id, task_id, date, agent, model, tier, strategy, usage {input, output,
  cache_read, cache_write}, cost, wall_seconds}` where `cost` is a number or
  the string `"n/a"`. Unknown fields are allowed and reported, never an error.
- An invalid file is rejected as a whole, with every problem listed (path and
  sentence), exit code 1.
- Prints progress per phase and overall (done weight over total weight; no
  tasks → "No plan") and run totals; `--json` for machines.
- `--expect <expected.json>` compares the result with a fixture's expected
  numbers and exits 1 on any difference.

**Fixture** `tools/test/fixtures/plan-v1/`: `plan.json` (invented project, 2
phases, 7 tasks over all statuses and sizes, 2 decisions, 3 runs, one with
`cost: "n/a"`), `expected.json` (progress per phase and overall, run count,
summed meters, summed priced cost, `usdStatus: "partial"`), and
`invalid-*.json` cases (wrong version, unknown enum, unknown phase, duplicate
id, `cost: 0` with no meters).

**HQ side (contract for the script, not code in this repo):**

- Opens the database read-only (SQLite URI `mode=ro`) and writes only the
  output file; it must not call HQ's id-assigning step. Items without a plan
  id are exported with `hq-<kind>-<row id>` and a `source` key, so a later
  import does not duplicate them.
- Maps worklog rows to `runs`: the four token columns to `usage`, `strategy`
  as is; `cost_usd` above 0 → the number; `cost_usd` 0 → `"n/a"` (HQ cannot
  tell 0 from unknown); `token_est` → `token_estimate`.
- Passes `arsenale plan-check out.json`; its own test exports HQ's invented
  test project and passes `--expect` against the same expected numbers.

Status mapping for the 1.4 import (recorded now so the fixture is right):
`todo`→`todo`, `doing`→`in_progress`, `review`→`in_review`,
`blocked`→`blocked`, `done`→`done`; Arsenale `backlog` exports as `todo`,
`cancelled` is left out of exports and counted.

## 9. Security and privacy

- Everything stays local; no new network call. The price defaults are a file
  in the package, fetched by the maintainers, never at run time.
- The price file is parsed with own keys only (`Object.hasOwn`), so a model
  named `constructor` or `__proto__` finds no price.
- Owner-only writes (`prices-init`, `savings-adopt`, `targetVersion`) go
  through `requireBoard`; an agent cannot plan a task into a version, mark a
  suggestion adopted or change prices.
- Context packs and reports never carry briefs, transcript text, command lines
  or secret-looking paths; packs are per project only.
- Reports and packs live in the data folder, under the existing owner-only

## 10. UI states

The Savings view is a new mode `sav` of the office page, listed under "More"
(beside "Tools & usage"); the top-bar change is a 1.4 decision. It reuses the
page margins of Activity, Version run and Tools & usage (`stage/style.cjs`).

| State | Shown |
|---|---|
| Empty (no finished runs) | "No runs logged yet. Savings start with your first logged runs." and a link to Settings > Connect your assistant |
| Runs, nothing measured | coverage "0 of N runs measured", spend "not recorded", no suggestions; a hint to report usage or allow a transcript folder |
| Measured, no prices | every money cell "n/a"; one notice "Prices are not set" with, for the owner, the button "Use list prices (Anthropic, fetched 2026-11-18)" |
| Partly priced | "≥ $X", "N of M runs unpriced", and the unpriced model names |
| Reported or estimated numbers | "reported" or "est." next to the number; estimated cost reads "about $X (est.)" |
| Plan pay model | "API-equivalent $X" |
| No suggestions | "No suggestions this week" with the rules checked |
| 375 px | one column; tables become stacked cards (label left, value right); no horizontal scroll; "Why?" opens inline, not as a pop-over |

Run detail (Tools & usage) gains the four meters, the cache-read share and
the cost source. The task form shows the six fields; the task list shows
`type`, `size` and `targetVersion` as chips. Every themed control, including
native select lists, takes the glass theme.
