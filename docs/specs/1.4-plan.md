## 1. Goal

1.3 gave tasks the schema-v1 fields and a ledger that prices them. 1.4 adds
the planning room, so the owner plans Arsenale's own next versions in
Arsenale instead of in HQ:

1. **Versions and phases** on files: a roadmap per project (Now / Next /
   Later), each version split into phases, tasks planned into a version.
2. **The Dock**: one screen that shows versions, phases, tasks, decisions and
   progress (done weight over total weight; "No plan" when empty), with cost
   from the 1.3 ledger.
3. **`arsenale import-plan` and `export-plan`**: a schema-v1 round trip, with a
   three-way conflict rule, so the owner's HQ export can be read in and the
   Dock can be written out.
4. **Today / Next** and a **work queue**: the owner approves tasks into an
   ordered queue; `arsenale next` gives the supervisor the next approved task
   with its context pack. The server starts nothing.
5. **Bug intake and owner-only "Plan into"**, and a **Proposals tray** where
   agents propose (a target version, a bug, a queue entry) and the owner
   approves.
6. A **release-notes draft** from a version's done tasks.
7. The **migration procedures M2 (shadow) and M3 (move the Arsenale
   project)**, with parity checks and rollback, which never read or write live
   HQ data.

Arsenale still watches only. Nothing in 1.4 starts, stops or steers an agent.

**IN**

- `arsenale today`, `arsenale next`, MCP `next_task`.
- MCP `propose_plan`; automatic bug proposals from "Pre-existing" findings of
  version runs; owner-only "Plan into".
- `arsenale release-notes <version>`.
- M2 shadow import and M3 promote and restore, as commands plus a written
  procedure (`docs/guide/plan-migration.md`).
- A string catalogue for every new UI string (`tools/strings/`), so a Persian
  locale can be added later without touching the views.
- Context pack: one added line with the current version and phase.

**OUT** (later or never)

- `minds` pack and `/minds`: 1.5 (migration plan 3.5).
- Per-tool `tierModels`, `providers.json`, memo and result reuse: 1.5.

  (migration decision 5a). 1.4 only makes the strings catalogue-ready; the
  English-only language test stays as it is.
- Any network call: no HQ API client, no GitHub sync, no live link (HQ
  decision 6a: file export and import only).
- The runner, claiming of tasks by a process, starting agents: 2.0.
- Dates, due-date timelines and Gantt views: the roadmap has no dates.
- Moving hire proposals into the Proposals tray: 1.5, with skill proposals.
- Writing `docs/specs/<version>-list.md` from the Dock: the supervisor still
  fills it (autonomous planning checklist); the Dock links a version to its
  version run by name.
- Projects other than the Arsenale project in M3 (that is M4, 1.5 onward).

## 3. Data model

All data stays in files under the data folder, written atomically
(`writeAtomic`) under the file's lock (`store.withLock`). The company
`schemaVersion` stays 1: every field below is optional and additive, so 1.3
(and 1.2) open a 1.4 folder without an error (section 3.6).

### 3.1 Versions and phases: `company/plan/<projectId>.json`

One file per project. One file per project keeps writes small and gives each
project its own master flag for M3 and M4.

```json
{
  "schemaVersion": 1,
  "projectId": "app-x",
  "master": "arsenale",
  "versions": [
    {
      "id": "v-2-1", "name": "2.1", "title": "Ordering", "goal": "Customers can order online",
      "horizon": "now", "status": "active", "order": 1,
      "phases": [
        { "id": "ph-1", "title": "Storefront", "goal": "Menu and order form", "order": 1, "status": "doing" },
        { "id": "ph-2", "title": "Delivery", "goal": "", "order": 2, "status": "todo" }
      ],
      "releasedAt": "", "planId": "", "source": "", "updatedAt": "2026-11-18T09:00:00Z"
    }
  ],
  "lastImport": null,
  "updatedAt": "2026-11-18T09:00:00Z"
}
```

| Field | Values | Rule |
|---|---|---|
| `name` | 1 to 20 characters of `[0-9A-Za-z.+-]` (the 1.3 `targetVersion` rule) | unique per project; it is the join key with `task.targetVersion` |
| `horizon` | `now`, `next`, `later` | the roadmap lane; no dates |
| `status` | `planned`, `active`, `released`, `dropped` | at most one `active` per project; `released` sets `releasedAt` |
| `order` | whole number | order inside a lane; ties break by name, numeric parts compared as numbers |
| `phases[].status` | `todo`, `doing`, `done` | derived on read when the phase has tasks (HQ's `sync_phase` rule: all done → done, all todo → todo, else doing); stored only for a phase with no tasks |
| `master` | `arsenale`, `import` | `import` marks a plan that came from another planner and is still mastered there (shown in a banner) |
| `planId`, `source` | text, at most 60 and 120 characters | set by `import-plan`; keep re-imports from duplicating |

A version named in a task's `targetVersion` but absent from the file is shown
as an **unlisted version** in the Later lane, with the owner button "Add to
roadmap". So 1.3 data, which has `targetVersion` but no plan file, shows up in
the Dock without a migration.

### 3.2 Task fields (adds to 1.3 section 3.4)

| Field | Values | Who sets it |
|---|---|---|
| `targetVersion` (1.3) | version name | board only, through "Plan into" or the task form |
| `phaseId` | a phase id of the task's target version | board only; cleared when `targetVersion` changes |
| `ownerTask` | `true` | board; import maps schema `owner: owner` to it, and export maps it back |
| `planId`, `source` | as in 3.1 | `import-plan` only |
| `missingInImport` | `true` | `import-plan` only: the item is gone from the last imported file (section 5.4) |

Supervisor and agent permissions are unchanged from 1.3 (supervisor: five
fields on create, never `targetVersion` or `phaseId`; agent: comments only).
`tasks.cjs` enforces them; a refused change writes nothing.

### 3.3 Decisions

Plan decisions use the existing decision records (`agent-runs/decisions/`,
`saveDecision`) with additive fields: `options` (list of at most 8 texts of
at most 60 characters), `recommendation`, `answer`, `planId`, `source`,
`targetVersion`. `state: open` maps to schema `status: open`, `taken` to
`decided`. An imported decision never opens a gate by itself: the Dock shows
it in the version's decisions panel, and the owner may press "Ask in
Decisions", which opens a choice gate with the same options (the existing
decision letter), or "Decide here", which records the answer.

### 3.4 Progress

- Weight per task: `S` 1, `M` 3, `L` 8. A task without a size counts 1 and
  the Dock says "N tasks have no size (counted as 1)" (the 1.3 ledger rule).
  HQ always stores a size (its default is M), so imported plans have no
  unsized tasks and the parity numbers of section 9 are not affected.
- Cancelled tasks are left out of both sums.
- Version progress = done weight / total weight of tasks whose
  `targetVersion` is the version; phase progress the same over tasks with
  that `phaseId`; tasks of the version without a phase form "No phase".
- No tasks → **"No plan"**, never "0 %". All done → "100 %, ready to
  release" (the release itself stays Gate C).
- One function, `plan.progress(tasks)`, is used by the Dock, `arsenale plan`,
  `export-plan` and the ledger's version rows, so the numbers agree.

### 3.5 Queue: `company/queue.json`

```json
{ "entries": [ { "taskId": "NW-12", "approvedAt": "2026-11-18T09:10:00Z", "approvedBy": "board", "claimedBy": "", "claimedAt": "" } ], "updatedAt": "..." }
```

Order is the list order. At most 200 entries. A task appears at most once.
An entry whose task is `done` or `cancelled` is hidden on read and dropped on
the next write. Section 7 has the rules.

### 3.6 Compatibility

- **1.3 opens 1.4 data unchanged.** 1.3 ignores `company/plan/`,
  `company/queue.json` and the new task and decision fields. 1.3's
  `updateTask` writes the whole task object back, so the new fields survive a
  1.3 edit. A proposal gate (section 8) shows in 1.3 as a plain approval
  question; answering it there records the answer and applies nothing, and
  1.4 then shows it as "Answered in an older dashboard: apply now?".
- **1.4 opens 1.3 data unchanged.** No plan file reads as "no versions";
  `targetVersion` values become unlisted versions; no queue reads as empty.
- **Reading never writes.** The Dock, Today, `next` without `--claim`,
  `export-plan`, `plan-parity` and the release-notes draft compute on read.
- A test runs the 1.3 code (read with `git show` at the `rel/1.3` merge
  commit, as `ledger-compat.test.cjs` does for 1.2.2) against a folder 1.4
  wrote, and skips with a reason when git or the commit is missing.

## 4. The Dock (screen "Plan")

### 4.1 Place and navigation

The top bar becomes **Campus, Plan, Live, Decisions, Team** (next-version
plan decision 6a). Office is reached by clicking an office on the campus, as
today, and is also listed first under "More", so no route is lost. The Plan
screen has five tabs: **Roadmap, Version, Today, Queue, Proposals** (the
Proposals tab shows its count). A project picker (glass listbox) sits on the
left of the tabs; with one project it is a plain label.

### 4.2 Roadmap

Three lanes, **Now, Next, Later**, each a column of version cards at 1366 px
and a stacked section at 390 px. A card shows: name and title, status chip,
progress ring with percent (or "No plan"), done/total weight, open decisions
count, blocked count, and cost from `ledger(by: version)` with the 1.3
display rule ("$X", "≥ $X", "n/a", "not recorded"; never "$0.00" for an
unpriced or unmeasured version). Released versions fold into "Released (N)"
at the bottom of Now. Owner actions: "New version", "Move to Next/Later/Now"
(buttons; at 1366 px also drag), "Edit", "Drop".

### 4.3 Version

- **Ship view** (default at widths ≥ 900 px): one ship, one hull section per
  phase in order, each filled to its percent, with the phase title and
  "done/total" under it; "No phase" is the last section when it has tasks.
  The ship is an SVG with a text equivalent (`role="img"` and a label that
  reads every section's numbers). It is a view, never the only way to read
  the data.
- **Table view** (default below 900 px, a toggle at any width): phases as
  groups, each with its tasks: id, title, status, type, size, tier, owner
  chip, and the per-task `tokenEstimate` against measured tokens from the
  ledger. At 390 px rows become cards (label left, value right).
- **Decisions panel**: open decisions of the version first (question,
  options, recommendation, "Ask in Decisions", "Decide here"), then decided
  ones folded.
- **Header**: progress, cost, the linked version run (a version run whose
  `version` equals the name, read-only link to the Version run view), and
  the owner buttons "Draft release notes" (section 9), "Queue next phase"
  (section 7), "Edit".
- **Banners**: for `master: import`, "Planned in another tool. Changes made
  here may be overwritten by the next import." For an M2 shadow, "Shadow copy
  of HQ. HQ is the master; editing is off." For a 1.3-written folder that is
  read-only (`readOnly`), the existing read-only notice.

### 4.4 Design rules (owner's, apply to every Plan screen and every slice)

1. **Glass on every widget**, including dropdown lists. A native `<select>`
   popup ignores CSS, so every select on a Plan screen is enhanced by
   `tools/pages/stage/listbox.cjs`: a button plus an ARIA listbox drawn with
   the glass tokens of `stage/glass.cjs` (background, blur, border, shadow,
   focus ring). Keyboard: Up, Down, Home, End, type-ahead, Enter, Escape;
   the native select stays in the DOM, hidden, as the form value. The same
   applies to menus, pop-overs, tooltips, confirm dialogs (no `alert` or
   `confirm`) and scrollbars inside Plan panels.
2. **Every screen designed and checked at 390 px (phone) and 1366 px
   (Windows desktop)**, with no horizontal page scroll at either width. The
   ui test (P3) loads each Plan tab and state at 390×844 and 1366×768 and
   asserts `documentElement.scrollWidth <= innerWidth`, saves a screenshot of
   each, and asserts that no native select is visible and that an opened
   listbox carries the glass class. At 390 px every action stays available
   (buttons instead of drag); planning on the phone is not read-only.
3. **English UI by default, strings catalogue-ready for Persian.** Every
   string a person reads goes through `T(key)`; the keys are collected in
   `tools/strings/catalogue.json` by `node tools/strings/extract.cjs`, and a
   fast test fails when a Plan view has a key missing from the catalogue or
   a bare text literal outside `T()`. Layout uses CSS logical properties
   (`margin-inline-start`, `inset-inline-end`, `text-align: start`) and
   direction-neutral icons, so an RTL locale is additive. Numbers go through
   the existing `digits()`. No Persian text ships in 1.4, and
   `language.test.cjs` is unchanged.

## 5. `arsenale import-plan` and `arsenale export-plan`

### 5.1 Commands

```
arsenale import-plan <file> --project <id> (--phases-as versions | --version <name>) [--dry-run] [--shadow] [--promote] [--json]
arsenale export-plan --project <id> (--phases-as versions | --version <name>) [--out <file>] [--force] [--json]
```

- `import-plan` reads one JSON file the owner names (5 MB and 10,000 items
  at most, `plan-schema.check`); an invalid file is refused as a whole with
  every problem listed, exit 1, and nothing is written.
- Writing needs the owner (`ARSENALE_BOARD_TOKEN`, as other board CLI
  writes); `--dry-run` needs no key, writes nothing and prints what would
  change. Exit codes: 0 done, 1 invalid or refused, 2 done with conflicts.
- `export-plan` writes JSON to stdout or to `--out` (refuses to overwrite an
  existing file without `--force`). It passes `plan-check`.

### 5.2 Mapping (schema v1 ⇄ Arsenale)

Schema v1 has phases but no versions. The owner says which they are:

- `--phases-as versions` (HQ plans the Arsenale project as one phase per
  version): each schema phase becomes a version. Its name is the phase's
  `version` field when present, else the first `\d+(\.\d+){1,3}` in its title
  ("v2.1 Ordering" → "2.1", title "Ordering"); a phase giving neither is
  refused, naming it. Its tasks get that `targetVersion` unless they carry a
  different `target_version`, which wins and is listed. Arsenale's own phases
  inside versions are exported under the top-level key `arsenale.phases`
  (an unknown field: plan-check reports it, HQ ignores it) and read back from
  there, so the round trip keeps them.
- `--version <name>`: the schema phases become the phases of that one
  version (created if missing); tasks without a phase go to "No phase".
- With neither flag and a file that has phases, the import is refused with
  "Say how to read the phases: --phases-as versions, or --version <name>".

| Schema v1 | Arsenale |
|---|---|
| task `id` | `planId`; the Arsenale id is allocated (`NW-13`) and never reused |
| task `status` todo, doing, review, blocked, done | `todo`, `in_progress`, `in_review`, `blocked`, `done` (1.3 section 7) |
| Arsenale `backlog` | exported `todo` plus `arsenale_status: "backlog"`, read back from there |
| Arsenale `cancelled` | left out of exports and counted in the export summary |
| `notes` | `description` (8,000 characters) |
| `owner: owner` / `agent` | `ownerTask: true` / absent |
| `token_estimate` | `tokenEstimate` |
| `type`, `size`, `tier`, `acceptance` | same fields |
| decision | decision record (3.3) |
| `runs` | not added to the ledger (that would count foreign runs as Arsenale's); kept read-only in `company/plan/<projectId>.worklog.json`, shown as "Imported worklog", and exported again unchanged together with the ledger rows of the project's tasks |
| `source` (any item) | `source`; export writes it back |
| `updated_at` | compared with `updatedAt` (5.3); export writes `updatedAt` as `updated_at` |

Matching an item in the file to an Arsenale item, in order: same `planId` in
the project; else a task whose Arsenale id equals the file id and which has
no `planId` (an Arsenale export read back in); else new.

### 5.3 Conflict rule (three-way, as HQ's sync)

After each import, `company/plan/.import-base/<projectId>.json` stores the
merged fields of every imported item as the **base**. On the next import, per
field:

| File vs base | Arsenale vs base | Result |
|---|---|---|
| changed | unchanged | take the file |
| unchanged | changed | keep Arsenale |
| changed | changed, different values | the newer of the file's `updated_at` and Arsenale's `updatedAt` wins; with either missing or equal, **Arsenale wins**; the conflict is listed |
| no base (first import of the item) | n/a | take the file |

Fields compared: title, status, type, size, tier, owner, target version,
phase, acceptance, description, token estimate; for decisions question,
options, recommendation, status, answer; for versions and phases title, goal,
status (stored only), horizon. Every write goes to the task's `history` with
`by: "import"`. `lastImport` in the plan file records the time, the file's
base name and SHA-256 (never its path), counts and the conflict list.

### 5.4 Never deletes

An Arsenale item with a `planId` that is missing from the new file is flagged
`missingInImport` and shown "Gone from the import file?" with the owner
buttons "Keep" (clears the flag) and "Cancel task". Flagged items are left
out of the next `export-plan` until kept. Native Arsenale items (no
`planId`) are never flagged.

### 5.5 Round trip

For a fixed mode: `export → import into an empty project → export` gives the
same file, except `updated_at` values and the allocated Arsenale ids where
the first export had none (P2 test on the 1.3 fixture `plan-v1/plan.json`).

## 6. Today / Next

`arsenale today [--json]`, `GET /api/today`, and the Today tab. Across
projects whose status is not done, archived or paused (HQ `today_board`
parity):

| Group | Contents |
|---|---|
| Doing | tasks `in_progress`, newest change first |
| Next up | the queue head (section 7), then suggestions: per project at most 2 `todo` tasks of the `now` versions, the `active` one first, by phase order, priority, age; at most 20. Suggestions are labelled "not queued" and carry the owner button "Queue" |
| Waiting for you | open gates (the existing rail), tasks `in_review`, `ownerTask` tasks not done, open plan decisions |
| Blocked | tasks `blocked`, and claimed queue entries with no linked run for 24 hours ("claimed, no run since …"); nothing is changed by itself |

The campus "Waiting for you" rail is unchanged; Today links to it.

## 7. Work queue and `arsenale next`

- **Approve** (owner only): "Queue" on a task, "Queue next phase" on a
  version (adds the phase's open `todo` tasks in table order), and "Queue"
  on a Today suggestion. Only `todo` and `backlog` tasks can be queued. Also
  reorder (up/down buttons; drag at 1366 px), remove, clear.
  `POST /api/queue {op: add|remove|move|clear}` (board), and `arsenale queue
  [add|remove|move|clear]` with the owner key.
- **`arsenale next [--project <id>] [--claim] [--release <taskId>] [--json]`**
  and MCP **`next_task {project?, claim?}`**: return the first unclaimed
  entry (optionally of one project) as:
  - `task`: id, title, description (clipped to 2,000 characters), acceptance,
    type, size, tier, target version, phase title, kind, assignee, office;
  - `position` and `queueLength`;
  - `context`: the project's context pack (`context-pack.build`, at most
    1,500 tokens);
  - `howTo`: "start_job with task_id NW-12; finish_job when done".
  The task part is at most 500 tokens (chars/4), so one answer is at most
  2,000 tokens.
- `--claim` / `claim: true` (supervisor; refused for the agent role): sets
  `claimedBy` and `claimedAt` and moves the task to `in_progress` through
  `updateTask` as the supervisor, which writes its history. `--release`
  clears a claim. A claim lasts until the task leaves `in_progress` or is
  released.
- An empty queue answers "The queue is empty: the owner approves tasks into
  it on the Plan screen." `next` never picks an unapproved task.
- **The server starts nothing.** `next` prints; the supervisor (a chat
  assistant or a loop the owner runs) decides to work. The 2.0 runner will
  read the same file.

## 8. Bug intake, "Plan into" and the Proposals tray

- **Bug intake**: a task with `type: bug` from the dashboard, `arsenale task`
  or MCP `create_task` (1.3). Bugs with no `targetVersion` show in a "Not
  planned" group at the top of the Roadmap tab (count on the tab).
- **"Plan into…"** (owner only, two clicks): on a task card or bug, a glass
  listbox of the project's `planned` and `active` versions with
  **"Next patch"** first and preselected. Next patch is the active version's
  name with its last number plus one ("2.1" → "2.1.1", "2.1.1" → "2.1.2");
  choosing it creates that version (horizon Now, status planned) when it
  does not exist. A second listbox offers the version's phases (optional).
- **Proposals** are gates with `approvalType: "proposal"` and a
  `proposal: {kind, payload, why, evidence}` object, so each opens in the
  existing decision letter (who asks, what happens, what if no). Kinds:
  - `plan_into`: `{task_id, target_version, phase?}`;
  - `bug`: `{title, description, project, target_version?}`;
  - `queue`: `{task_id}`.
- MCP **`propose_plan {kind, …, why}`** (supervisor and agents). Nothing is
  written but the gate. Limits: at most 50 waiting proposals per project
  (then 429), duplicates (same kind and payload) answer with the existing
  proposal.
- **Automatic bug proposals**: when a run that belongs to a version run
  finishes with findings starting "Pre-existing" (any case, also
  "[pre-existing]"), each such finding becomes one `bug` proposal (title =
  the finding, clipped to 200 characters; evidence = the run id), deduplicated
  by a hash of project and text, at most 20 per run.
- **Accept / Edit and accept / Decline** (owner only,
  `POST /api/proposal-decision`): accept applies through the same board code
  path as a manual action (create the bug task, set `targetVersion`, add the
  queue entry) and answers the gate; decline answers it. The answer reaches
  the proposer through `get_answers`, as every answer does.
- **Tray**: the Proposals tab lists waiting proposals, newest first, and the

## 10. Migration M2 and M3

Both are procedures the owner runs, written out in
`docs/guide/plan-migration.md` (invented names in examples) and backed by the
commands below. **Arsenale never reads or writes live HQ data**: it has no HQ
address, no HQ credentials and no network call. Its only input is a copy of
an export file that the HQ-side M1 script wrote (1.3 section 7). Any change
in HQ (for example making its planning pages read-only) is an owner step in
HQ, outside this repository.

### 10.1 Parity check

`arsenale plan-parity <hq-export.json> --project <id> (--phases-as versions | --version <name>) [--shadow] [--only-imported] [--json] [--write]`

1. `plan-schema.check(file)` gives the HQ side's numbers.
2. `export-plan` of the Arsenale side (or of the shadow with `--shadow`;
   only items carrying a `planId` with `--only-imported`) is checked the
   same way.
3. Compared: per phase and overall `tasks`, `doneWeight`, `totalWeight`,
   `percent`; task counts per status; decisions open and decided; the id
   sets (missing on either side); for every matched id the fields title,
   status, size, type, target version, phase; run count, the four meter
   sums, priced cost and `usdStatus`.
4. Output "Parity: clean" or "Parity: N differences" with each one listed;
   exit 0 clean, 1 different. `--write` saves the report to
   `<home>/plan-parity/<projectId>-<date>.json`.

### 10.2 M2: shadow (HQ is the master)

| Step | Who | What |
|---|---|---|
| 1 | Owner, in HQ | Run the M1 export for the `arsenale` project; copy the file to the Arsenale machine |
| 2 | Owner | `arsenale import-plan hq.json --project arsenale --phases-as versions --shadow` |
| 3 | Arsenale | Writes only `<home>/shadow/arsenale/` (plan, tasks, decisions, worklog, base). The live company folder is not touched. The Dock lists "arsenale (shadow of HQ)" read-only with the shadow banner |
| 4 | Owner | `arsenale plan-parity hq.json --project arsenale --phases-as versions --shadow --write`, daily, after a fresh export. Arsenale adds no scheduler: the owner uses their own (cron) or runs it by hand |
| 5 | Exit | M2 is clean after 14 consecutive daily reports with "Parity: clean" (the two-week shadow of the migration plan) and the owner's yes |

Rollback: `arsenale shadow drop --project arsenale` deletes
`<home>/shadow/arsenale/` and nothing else. HQ was never changed.

### 10.3 M3: move the Arsenale project (Arsenale becomes the master)

| Step | Who | What |
|---|---|---|
| 0 | Check | M2 clean (step 5); `arsenale plan-parity` clean on today's export |
| 1 | Owner, in HQ | Freeze planning of the `arsenale` project in HQ (HQ's own read-only setting); take the final export |
| 2 | Owner | `arsenale import-plan final.json --project arsenale --phases-as versions --promote` |
| 3 | Arsenale | Before any write, copies every file it will change and lists every file it will create into `<home>/backups/plan-m3-<stamp>/` with a manifest (paths relative to the data folder, SHA-256 of each). Then imports into the live company (section 5), sets `master: "arsenale"`, and drops the shadow folder |
| 4 | Arsenale | Runs `plan-parity final.json --only-imported`; a difference undoes step 3 at once from the backup and exits 1 |
| 5 | Owner | Works from the Dock. A schema-v1 export for HQ's read-only mirror is `arsenale export-plan`, if wanted |

Rollback: `arsenale plan restore plan-m3-<stamp>` (owner key) puts back every
copied file, removes every file the manifest says was created, and checks the
hashes; then the owner lifts the freeze in HQ. HQ data was never changed by
Arsenale, so HQ is current as of step 1.

## 13. Security and privacy

- The server still binds to 127.0.0.1 and checks the host header; every new
  route needs the launch key cookie; every write route is board only. The CLI
  writes need `ARSENALE_BOARD_TOKEN` (the owner's key); without it the
  caller is an agent and is refused, except `--dry-run` and reads.
- Owner-only, enforced in the modules and not in the UI: versions, phases,
  "Plan into", `phaseId`, queue changes, proposal decisions, imports,
  promote, restore, release-notes `--write`.
- Imported text is data: titles, notes and decisions are clipped to the task
  limits, never executed, and links in them are not followed. `source` and
  `planId` are checked against their patterns; file paths of imports are
  never stored (only base name and hash).
- Plan and queue files are parsed with own keys only (`Object.hasOwn`), so
  an id like `__proto__` matches nothing.
- `restore` only touches paths listed in its manifest, each resolved inside
  the data folder (`..` and links refused).
- No key, token or HQ address is read, stored or printed. No network call is
  added; the wording and language tests apply to every new file; fixtures use
  invented data.
